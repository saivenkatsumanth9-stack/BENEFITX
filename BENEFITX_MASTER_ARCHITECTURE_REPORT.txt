1. EXECUTIVE SUMMARY & MISSION
================================================================================
In India, the Central and State Governments disburse over ₹4.5 Lakh Crore ($54B+) 
annually across more than 1,000 welfare, educational, agricultural, and financial 
assistance schemes. Despite this, over 60% of eligible citizens fail to access 
these benefits due to discovery blindspots, bureaucratic jargon, and documentation 
rejections.

BENEFITX was engineered as an AI-powered Citizen Decision-Support & Readiness 
Platform to eliminate these bottlenecks through transparent, explainable, and 
deterministic algorithms. It never treats AI as a black box for official 
eligibility; instead, deterministic rule engines handle calculations while 
language models provide vernacular accessibility.

4.1 ALGORITHM 1: MISSED SCHEME DETECTOR & DETERMINISTIC PROFILE MATCHING
--------------------------------------------------------------------------------
File: `src/server/services/recommendationEngine.ts`

Purpose:
Proactively identifies schemes matching citizen profiles that users have not yet 
saved, searched, or tracked.

Mathematical Formulation:
The overall MatchScore is bounded between [5, 99] and calculated as:

   MatchScore = clamp(5, 99, round(0.50 * ProfileMatch + 0.35 * EligibilityMatch + 0.15 * DocReadiness))

Where:
1. ProfileMatch:
   ProfileMatch = round( ( SUM( Weight_i * StatusValue_i ) / SUM( Weight_i ) ) * 100 )

   Status Weights:
   - State: Weight = 1.4
   - Income: Weight = 1.2
   - Gender: Weight = 1.2
   - Farmer Status: Weight = 1.2
   - Age: Weight = 1.0
   - Education: Weight = 1.0
   - Occupation: Weight = 1.0
   - Area Type: Weight = 0.8
   - Additional Notes: Weight = 0.5

   Status Values:
   - "match": 1.0
   - "verify": 0.6
   - "unknown": 0.4
   - "mismatch": 0.0

2. EligibilityMatch:
   - If assessment status is "likely-eligible": 100
   - If assessment status is "needs-verification": 72
   - If assessment status is "likely-not-eligible": 38

3. Document Readiness:
   - Computed via Algorithm 3.

Classification Boundaries:
- POTENTIAL_MATCH : MatchScore >= 75
- PARTIAL_MATCH   : 50 <= MatchScore < 75
- UNLIKELY_MATCH  : MatchScore < 50

Semantic Rule:
Scores represent "Profile Match Percentage", never "Officially Eligible".

--------------------------------------------------------------------------------
4.2 ALGORITHM 2: TRI-STATE EXPLAINABLE ELIGIBILITY ENGINE
--------------------------------------------------------------------------------
File: `src/server/services/eligibilityEngine.ts`

Purpose:
Provides rule-by-rule evaluation comparing user attributes with scheme criteria 
under strict tri-state logic without coercing unknown fields into matches.

Logic Table:
- Condition Evaluation:
  * For Age: (AgeMin == undefined || Age >= AgeMin) && (AgeMax == undefined || Age <= AgeMax)
  * For Income: (IncomeMax == undefined || Income <= IncomeMax)
  * For State: (States == undefined || States.length == 0 || States.includes(UserState))
  * For Education: (Education == undefined || Education.includes(UserEducation))
  * For Occupation: (Occupations == undefined || Occupations.includes(UserOccupation))

Overall Status Determination:
   If (Count(MismatchConditions) > 0) -> FAILED
   Else If (Count(UnknownConditions) > 0 || Count(VerifyConditions) > 0) -> UNKNOWN
   Else -> MATCHED

Human-Readable Condition Formatter:
- "match": "[Label] matches: your value ([Val]) is within required range ([Req])"
- "mismatch": "[Label] does not match: your value ([Val]) does not satisfy ([Req])"
- "unknown": "[Label] required ([Req]) but was not provided in profile"
- "verify": "[Label] requires manual verification: [Req]"

--------------------------------------------------------------------------------
4.3 ALGORITHM 3: SMART DOCUMENT READINESS & VERIFICATION CALCULATOR
--------------------------------------------------------------------------------
File: `src/server/services/documentReadinessEngine.ts`

Purpose:
Evaluates required vs optional document availability to generate a quantitative 
readiness score.

Formulas:
1. Scheme Document Readiness Score:
   ReadinessScore = ( AvailableRequiredDocs / TotalRequiredDocs ) * 100

   * Where AvailableRequiredDocs includes status 'available' and 'needs-verification'.
   * If TotalRequiredDocs == 0, ReadinessScore = 100.

2. Neutrality of Optional Documents:
   Optional documents (e.g. Caste Certificate, Property Deed) are tracked in 
   `optionalAvailable` but strictly excluded from the denominator `TotalRequiredDocs`, 
   ensuring citizens are not penalized for missing optional certificates.

3. Composite Application Readiness Score (Used on Dashboard & Readiness Page):
   CompositeScore = round(0.40 * EligibilityScore + 0.40 * DocumentScore + 0.20 * VerificationScore)
   * Where VerificationScore = ( VerifiedDocsCount / TotalRequiredDocs ) * 100.

--------------------------------------------------------------------------------
4.4 ALGORITHM 4: ZERO-MUTATION WHAT-IF ELIGIBILITY SIMULATOR
--------------------------------------------------------------------------------
File: `src/server/services/simulationEngine.ts`

Purpose:
Allows citizens to simulate hypothetical life changes (e.g. income drop, 
graduating college, changing state of residence) to see which new schemes unlock.

Security & Mutation Guardrails:
1. Field Whitelist Enforcement:
   SIMULATION_WHITELIST = ['age', 'annualIncome', 'state', 'educationLevel', 
   'occupation', 'gender', 'areaType', 'isStudent', 'isFarmer', 'employmentStatus']

   Any field not in `SIMULATION_WHITELIST` is rejected.

2. Zero-Mutation Guarantee:
   SimulatedProfile = Object.assign({}, ActualProfile)
   ActualProfile remains immutable in memory.

3. Differential Output Computation:
   - NewPotentialSchemes = { Scheme | Score_simulated >= 55 && Score_actual < 55 }
   - RemovedPotentialSchemes = { Scheme | Score_actual >= 55 && Score_simulated < 55 }
   - ChangedSchemes = Sorted list of schemes where |Score_simulated - Score_actual| > 0

--------------------------------------------------------------------------------
4.5 ALGORITHM 5: MULTILINGUAL PLAIN-LANGUAGE TRANSLATION & SIMPLIFICATION
--------------------------------------------------------------------------------
File: `src/server/services/explanationEngine.ts`

Purpose:
Converts dense, bureaucratic gazette notices into plain, easy-to-understand 
language in English, Telugu, and Hindi.

Architecture Pipeline:
  [Gov Gazette PDF / Scheme Data]
               |
               v
  [Deterministic Eligibility Engine]
               |
               v
  [Structured Eligibility Criteria]
               |
               v
  [AI / Template Simplification Engine] (EN / TE / HI)
               |
               v
  [Plain-Language Citizen Output]

Translation Matrix Coverage:
- English (`en`): Conversational, 6th-grade reading level.
- Telugu (`te`): Full native Telugu script with customized Telugu welfare terminology.
- Hindi (`hi`): Full native Devanagari script with verified Hindi terms.

Graceful Degradation:
If `BENEFITX_AI_API_KEY` is not provided in `.env`, the engine falls back to a 
deterministic high-fidelity translation template engine with 100% uptime.

7.1 CHALLENGE 1: TanStack Router SSR Code-Splitting & Loader ReferenceErrors
--------------------------------------------------------------------------------
Symptom:
During SSR evaluation, route components utilizing `useParams({ from: '/schemes/$id' })` 
threw runtime `ReferenceError: getSyncRecommendation is not defined` when 
TanStack Router split code into `?tsr-split=component`.

Root Cause:
TanStack Start splits server and client bundles at the route boundary. Dynamic 
helper functions defined outside the exported component were stripped during SSR 
component extraction.

Resolution:
Refactored `src/routes/schemes/$id.tsx` and `src/routes/eligibility/$id.tsx` to use 
`createFileRoute().loader({ loader: ({ params }) => { ... } })` with synchronous 
data resolution and accessed data via `Route.useLoaderData()`. Re-exported the 
matching helper functions directly from `@/lib/matching`.

7.3 CHALLENGE 3: TypeScript 5.8 `exactOptionalPropertyTypes` Violations
--------------------------------------------------------------------------------
Symptom:
Running `npx tsc --noEmit` failed with multiple TS2375 and TS2322 errors:
`Type '{ ... fileName: undefined }' is not assignable to type 'UserDocument' with exactOptionalPropertyTypes: true`.

Root Cause:
TypeScript's `exactOptionalPropertyTypes: true` prohibits assigning explicit `undefined` 
to a property defined as `prop?: string`. It requires `prop?: string | undefined`.

Resolution:
Updated all interface declarations across `src/lib/types.ts` and `src/server/types.ts`:
- `fileName?: string | undefined;`
- `uploadedAt?: string | undefined;`
- `expiresAt?: string | undefined;`
- `details?: string | undefined;`
- Updated `SchemeCard.tsx` and `DocumentCard.tsx` props accordingly.

--------------------------------------------------------------------------------
7.4 CHALLENGE 4: TanStack Start `createServerFn` RPC Serialization Errors
--------------------------------------------------------------------------------
Symptom:
TypeScript compiler threw TS2345 in `missedSchemes.ts` and `simulation.ts`:
`Type 'unknown' is not assignable to type 'SerializationError<"Type may not be serializable">'`.

Root Cause:
TanStack Start's RPC compiler validates return types at compile-time to guarantee 
JSON serializability over the network. Using `unknown` or unstructured `Record<string, unknown>` 
in `ApiResponse` or `appliedChanges` triggers strict serialization errors.

Resolution:
1. Typed `ApiResponse<T>` with strict optional fields:
   `error?: { code: string; message: string; details?: string | undefined } | undefined;`
2. Explicitly typed simulation change values in `src/server/types.ts`:
   `appliedChanges: Record<string, { from: string | number | boolean | null; to: string | number | boolean | null }>;`
3. Ensured all server functions return strict JSON-serializable primitives.

--------------------------------------------------------------------------------
7.5 CHALLENGE 5: Database Layer Decoupling (Mock -> Supabase Transition)
--------------------------------------------------------------------------------
Symptom:
Initial user prompt requested Supabase RLS policies and SQL migrations, but the 
codebase had no Supabase libraries or connection keys.

Resolution:
Architected a modular service layer decoupling data access from business logic. 
All 5 backend engines (`recommendationEngine`, `eligibilityEngine`, `documentReadinessEngine`, 
`simulationEngine`, `explanationEngine`) operate on normalized `Scheme[]` and `UserProfile` 
interfaces. When Supabase keys are configured in `.env`, the data provider can be 
swapped to `supabase.from('schemes').select('*')` without altering API contracts 
or breaking frontend components.

--------------------------------------------------------------------------------
7.6 CHALLENGE 6: Zero-Mutation Isolation in What-If Simulator
--------------------------------------------------------------------------------
Symptom:
Risk of shallow object mutation where modifying `simulatedProfile.annualIncome` 
could accidentally mutate the stored citizen state in memory.

Resolution:
Implemented defensive cloning inside `simulateEligibility()`:
1. Created shallow profile clone: `const simulatedProfile = { ...actualProfile };`
2. Filtered inputs through `SIMULATION_WHITELIST` to prevent parameter injection.
3. Created dedicated test `should return simulation results without modifying actual profile` 
   verifying that `actualProfile.annualIncome` remains identical before and after.

9. SECURITY, ROLE-BASED ACCESS CONTROL & PRIVACY GUARDRAILS
================================================================================
1. Input Validation:
   Every server function parameter is validated using Zod (`safeParse`). Invalid 
   payloads are rejected before execution.

2. Deterministic AI Guardrails:
   AI is strictly prohibited from deciding official citizen eligibility. AI is 
   used solely for plain-language simplification and language translation.

3. Simulation Field Whitelisting:
   Prevents parameter pollution and ensures only valid demographic fields can be 
   simulated.

4. Role-Based Access Control (RBAC):
   - `requireAuth()`: Ensures valid user session context.
   - `requireAdmin()`: Restricts document approval/rejection actions to nodal 
     officers.

5. Data Privacy & Scope:
   Document readiness operations strictly evaluate metadata within the caller's 
   scope; no cross-citizen document leakage is possible.
